# Где маркетплейсу улучшать доставку

Я взял данные бразильского маркетплейса Olist, чтобы понять, как связаны опоздания доставки и оценки покупателей. Мне хотелось найти конкретное направление, которое команда логистики могла бы проверить первым. Весь анализ я сделал на PostgreSQL и собрал интерактивный дашборд.

[HTML-дашборд](dashboard/index.html) · [SQL-запросы](sql/05_explore.sql) · [Таблица приоритетов](results/priority_queue.csv)

## Данные

В исходных файлах **99 441 заказ**. Для анализа я связал заказы с отзывами, покупателями и товарами. Покупки в итоговой витрине датируются **15.09.2016–29.08.2018**. Помесячный график начинается с января 2017 года, когда в данных уже было больше заказов. [Описание датасета Olist](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce)

## Как я подготовил данные

1. Из 96 478 заказов со статусом «доставлен» я убрал восемь, у которых отсутствовала дата доставки. Опоздание считал в календарных днях. Доставку в обещанный день считал своевременной.
2. Собрал витрину с одной строкой на заказ. Если покупатель оставил несколько ответов, я брал последний по времени. **646 заказов без ответа** оставил в расчёте доли опозданий. Для доли оценок 1–2 использовал заказы с оценкой.
3. Назначал категорию, когда она известна и одинакова для всех позиций заказа. Таких заказов получилось **94 358**. В срезе по штатам использовал штат покупателя.
4. Нашёл три оценки с временем ответа до покупки. Они остались в общем расчёте. В дополнительный срез я включил только ответы с момента фактической доставки. [Покрытие и проверенные аномалии](results/coverage.csv)

## Что получилось

### При опоздании низкие оценки встречались чаще

Позже обещанной даты доставили **6 534 из 96 470 заказов (6,77%)**. Среди заказов с оценкой доля оценок 1–2 составила **62,42% при опоздании и 9,27% при доставке в срок**. Разница — **53,15 п. п.** Во всех **69 парах «штат × категория»**, где было от 100 доставок и хотя бы по 20 оценённых заказов в каждой группе, низкие оценки встречались чаще при опоздании. Эти пары охватывают 3 738 из 6 381 оценённого заказа с опозданием (58,58%).

### Оценки по длительности опоздания

| Опоздание | Доставлено | Оценки 1–2 среди оценённых | Оценки 1–2 среди ответов после доставки |
| --- | ---: | ---: | ---: |
| В срок или раньше | 89 936 | 9,27% (8 289 из 89 443) | 9,25% (8 258 из 89 263) |
| 1–2 дня | 1 370 | 25,44% (345 из 1 356) | 18,27% (216 из 1 182) |
| 3–7 дней | 2 302 | 63,86% (1 433 из 2 244) | 20,31% (132 из 650) |
| 8+ дней | 2 862 | 79,29% (2 205 из 2 781) | 30,26% (23 из 76) |

В группе 8+ дней я заметил, что **2 705 из 2 781** ответов появились до фактической доставки. У 2 680 из этих заказов обещанная дата уже прошла. По описанию Olist, опрос могли отправить после получения заказа или в обещанный срок. Поэтому я отдельно посчитал долю низких оценок среди ответов после вручения. Она также растёт с длительностью опоздания. У самой длинной задержки в этом срезе всего 76 ответов. Я трактую результат как связь между сроком и оценкой, потому что на оценку также могли влиять качество товара и другие особенности заказа. [Описание датасета Olist](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce)

### Больше всего проблемных заказов было в RJ и SP

RJ и SP дали **2 035 из 3 983 заказов с опозданием и оценкой 1–2 (51,1%)**. В RJ таких заказов было 1 064 при 12 350 доставках, в SP — 971 при 40 494 доставках. Доля опозданий составила 12,11% в RJ и 4,49% в SP. На первые девять штатов рейтинга пришлось 82,32% всех случаев.

Я бы начал с категории **«Текстиль для спальни, стола и ванной» (`bed_bath_table`)** у покупателей в RJ. Из 1 330 заказов этой категории 201 опоздал, 142 получили 1–2 звезды при опоздании. На продавцов из SP приходится **133 из этих 142 случаев (93,7%)**. Для 1 163 заказов этого направления доля опозданий составила 16,17% (188 заказов). Я бы проверил время до передачи перевозчику и время в пути. Штат продавца здесь служит приближением к точке отправления. Для проверки маршрута нужны фактический склад и события перевозчика. [Таблица приоритетов](results/priority_queue.csv)

### Больше всего опаздывали заказы, купленные в марте 2018 года

В марте опоздали **1 328 из 7 003 заказов (18,96%)**. Это на 4,84 п. п. выше февраля. За январь–март доля составила 12,88% от общего числа доставок за три месяца. В марте 21,17% оценённых заказов получили 1–2 звезды. Месяц я определял по дате покупки.

## Что я бы проверил дальше

Я бы протестировал уведомление об обновлённом сроке для покупателей, чьи заказы рискуют опоздать. Для пилота случайно разделил бы их на две группы. Одна получала бы текущие уведомления, вторая — сообщение об обновлённом сроке. Основная метрика — доля заказов с обращением «Где мой заказ?». Дополнительно я бы отслеживал долю оценок 1–2 и долю ответивших на опрос. Для пилота понадобятся данные об обращениях и отправленных уведомлениях.

## Как считаются метрики

| Метрика или правило | Как я её считаю |
| --- | --- |
| Единица анализа | Один заказ со статусом `delivered`, известными датами покупки, обещанной и фактической доставки. Даты доставки должны быть не раньше даты покупки. |
| Дни опоздания | Календарная дата фактической доставки минус обещанная дата. Доставку в обещанный день считаем своевременной. |
| Доля опозданий | Заказы с положительной разницей дат / все доставленные заказы в выборке. |
| Доля оценок 1–2 | Заказы с последней оценкой 1 или 2 / заказы с оценкой. При нескольких ответах берём последний по времени ответа. |
| Ответы после доставки | Последний ответ получен в момент фактической доставки или позже, по времени из CSV. |
| Штат и категория | Штат покупателя. Категорию назначаем, если она известна и одинакова для всех позиций заказа. |
| Приоритет сегмента | Число заказов с опозданием и оценкой 1–2. Минимум 100 доставленных и 20 оценённых опоздавших заказов. Срезы по штату, категории и их пересечению ранжируются отдельно. |

## Какие приёмы SQL я использовал

- `DISTINCT ON` для выбора последнего ответа по заказу.
- Календарный CTE на `generate_series()` и `LAG()` для сравнения соседних месяцев.
- `SUM() OVER` для подсчёта доли опозданий за три месяца и накопительного вклада штатов.
- `ROW_NUMBER()` для рейтинга штатов и товарных сегментов. Оконные итоги я считал по всем сегментам, прошедшим пороги, до вывода первых десяти.

## Запуск на PostgreSQL

Понадобятся запущенный PostgreSQL, клиент `psql` и Python 3.10 или новее. Скачать и распаковать исходные CSV. Из корня проекта выполнить команды PowerShell, подставив путь к CSV и параметры подключения к своему серверу. Отдельную базу проекта достаточно создать один раз. [Olist на Kaggle](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce)

```powershell
createdb -h localhost -U postgres olist_delivery
python .\scripts\build.py --data-dir 'C:\path\to\olist-csv' --host localhost --user postgres --dbname olist_delivery
psql -h localhost -U postgres -d olist_delivery -v ON_ERROR_STOP=1 -f .\sql\05_explore.sql
python .\dashboard\build_dashboard.py
```

Если `psql` находится вне `PATH`, для сборки можно передать полный путь к нему через `--psql`. При нестандартном порте добавить `--port` к команде сборки и `-p` к командам PostgreSQL.

Я использовал Python для подготовки CSV, запуска `psql` и сборки дашборда. Расчёты находятся в SQL. Сборка загружает CSV через `\copy` и пересоздаёт таблицы и представления проекта в схеме `olist_delivery`. При ошибке загрузки или проверки PostgreSQL откатывает транзакцию. [Документация PostgreSQL по psql](https://www.postgresql.org/docs/current/app-psql.html)
