# Где маркетплейсу улучшать доставку

Проект на PostgreSQL и данных бразильского маркетплейса Olist. Задача команды продукта и логистики — понять, как связаны опоздания с оценками 1–2, и выбрать направление, которое стоит проверить первым.

[HTML-дашборд](dashboard/index.html) · [SQL-запросы](sql/05_explore.sql) · [Таблица приоритетов](results/priority_queue.csv)

## Что показали данные

- **6 534 из 96 470 заказов (6,77%)** доставили позже обещанной даты. Среди оценённых заказов доля оценок 1–2 составила **62,42% при опоздании и 9,27% при доставке в срок**. Разница — **53,15 п. п.**
- **RJ и SP дали 2 035 из 3 983 заказов с опозданием и оценкой 1–2 (51,1%)**. В RJ таких заказов 1 064 при 12 350 доставках, в SP — 971 при 40 494 доставках. Срок нарушен у 12,11% доставок в RJ и у 4,49% в SP. На первые девять штатов рейтинга приходится 82,32% всех случаев.
- **Первый сегмент для проверки — покупатели из RJ, категория «Текстиль для спальни, стола и ванной» (`bed_bath_table`).** Из 1 330 заказов 201 доставили с опозданием, 142 из них получили 1–2 звезды. На продавцов из SP приходится 133 из этих 142 случаев (93,7%).
- В помесячном ряду пик доли опозданий пришёлся на **март 2018 года** — 1 328 из 7 003 заказов (18,96%, на 4,84 п. п. выше февраля). За январь–март доля составила 12,88%, если считать её от общего числа доставок за три месяца. В марте 21,17% оценённых заказов получили 1–2 звезды. Месяц считается по дате покупки.
- Во всех **69 парах «штат × категория»**, где было от 100 доставок и хотя бы по 20 заказов с оценкой в каждой группе по сроку, доля оценок 1–2 выше при опоздании. Эти пары охватывают 3 738 из 6 381 опоздавшего заказа с оценкой (58,58%). Сравнение описывает связь в сегментах, которые прошли пороги.

### Оценки по длительности опоздания

| Опоздание | Доставлено | Оценки 1–2 среди оценённых | Оценки 1–2 среди ответов после доставки |
| --- | ---: | ---: | ---: |
| В срок или раньше | 89 936 | 9,27% (8 289 из 89 443) | 9,25% (8 258 из 89 263) |
| 1–2 дня | 1 370 | 25,44% (345 из 1 356) | 18,27% (216 из 1 182) |
| 3–7 дней | 2 302 | 63,86% (1 433 из 2 244) | 20,31% (132 из 650) |
| 8+ дней | 2 862 | 79,29% (2 205 из 2 781) | 30,26% (23 из 76) |

В группе 8+ дней **2 705 из 2 781** ответов были отправлены до фактической доставки. У 2 680 из этих заказов обещанная дата уже прошла. По описанию Olist, опрос могли отправить как после получения заказа, так и в момент наступления обещанного срока. В разрезе после доставки сохраняется рост доли низких оценок, но группа 8+ дней сокращается до 76 ответов и отличается по составу. Эти сравнения описывают связь, а на оценки также могли повлиять качество товара и другие особенности заказа. [Описание датасета Olist](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce)

## Что проверить дальше

1. **Начать с направления SP → RJ в категории `bed_bath_table`.** Для 1 163 заказов этого направления доля опозданий составила 16,17% (188 заказов). Разобрать шаги от покупки до передачи перевозчику и от передачи до доставки. Штат продавца служит приближением к точке отправления. Для проверки конкретного маршрута нужны фактический склад и события перевозчика.
2. **Проверить уведомление о риске опоздания.** В будущем пилоте случайно разделить покупателей, чьи заказы рискуют выйти за обещанный срок, на группы с текущими уведомлениями и с проактивным сообщением об обновлённом сроке. Основная метрика — доля включённых в пилот заказов с обращением «Где мой заказ?». Дополнительно отслеживать долю оценок 1–2 и долю ответивших на опрос. Данные с обращениями и событиями уведомлений потребуется собрать для пилота.

## Как считаются метрики

| Метрика или правило | Определение |
| --- | --- |
| Единица анализа | Один заказ со статусом `delivered`, известными датами покупки, обещанной и фактической доставки. Даты доставки должны быть не раньше даты покупки. |
| Дни опоздания | Календарная дата фактической доставки минус обещанная дата. Доставку в обещанный день считаем своевременной. |
| Доля опозданий | Заказы с положительной разницей дат / все доставленные заказы в выборке. |
| Доля оценок 1–2 | Заказы с последней оценкой 1 или 2 / заказы с оценкой. При нескольких ответах берём последний по времени ответа. |
| Ответы после доставки | Последний ответ получен в момент фактической доставки или позже, по времени из CSV. |
| Штат и категория | Штат покупателя. Категорию назначаем, если она известна и одинакова для всех позиций заказа. |
| Приоритет сегмента | Число заказов с опозданием и оценкой 1–2. Минимум 100 доставленных и 20 оценённых опоздавших заказов. Срезы по штату, категории и их пересечению ранжируются отдельно. |

В исходных файлах 99 441 заказ. Из 96 478 заказов со статусом «доставлен» восемь исключены из-за отсутствующей даты доставки. В витрине осталось 646 заказов без ответа и 94 358 заказов с одной известной категорией. Проверка нашла три оценки с временем ответа до покупки. Они сохранены в основном расчёте и исключены самим условием из среза после доставки. Покупки в витрине датируются **15.09.2016–29.08.2018**. График начинается с января 2017 года из-за малого объёма ранних месяцев. [Покрытие и аномалии](results/coverage.csv)

## Запуск на PostgreSQL

Понадобятся запущенный PostgreSQL, клиент `psql` и Python 3.10 или новее. Скачать и распаковать исходные CSV. Из корня проекта выполнить команды PowerShell, подставив путь к CSV и параметры подключения к своему серверу. Отдельную базу проекта достаточно создать один раз. [Olist на Kaggle](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce)

```powershell
createdb -h localhost -U postgres olist_delivery
python .\scripts\build.py --data-dir 'C:\path\to\olist-csv' --host localhost --user postgres --dbname olist_delivery
psql -h localhost -U postgres -d olist_delivery -v ON_ERROR_STOP=1 -f .\sql\05_explore.sql
python .\dashboard\build_dashboard.py
```

Если `psql` находится вне `PATH`, для сборки можно передать полный путь к нему через `--psql`. При нестандартном порте добавить `--port` к команде сборки и `-p` к командам PostgreSQL.

Сборка загружает CSV клиентской командой `\copy` и пересоздаёт таблицы и представления проекта в схеме `olist_delivery`. При ошибке загрузки или проверки PostgreSQL откатывает транзакцию. Расчёты выполняются в SQL. Python подготавливает входные файлы, запускает `psql` и сохраняет агрегаты для отчётности. [Документация PostgreSQL по psql](https://www.postgresql.org/docs/current/app-psql.html)

В [05_explore.sql](sql/05_explore.sql) календарный CTE на `generate_series()` и `LAG()` сравнивают соседние месяцы. `SUM() OVER` считает трёхмесячную долю опозданий из сумм заказов и накопительный вклад штатов. Сравнение внутри штатов и категорий использует `ROW_NUMBER()` для вывода первых десяти сегментов и оконные итоги для подсчёта всех сегментов, прошедших пороги.

Готовый HTML-дашборд можно открыть локально из [dashboard/index.html](dashboard/index.html). CSV с результатами лежат в [results](results/).
